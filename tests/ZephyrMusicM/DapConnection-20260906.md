# 2026-09-06 DAP 连接排查补充

用户确认接头紧固且无人移动，不能把连接失败直接归因于接线。后续已通过实体RESET接管、烧入默认不加热固件并完成日志导出，见 [恢复记录](Recovery-20260906.md)。以下保留恢复前的诊断过程，不能把当时的“尚未恢复”当成最新状态。

已得到的实测结果：

- UART8 曾重新收到旧准备固件输出，14.105秒时 IMU序号6952、温度36.25℃、加热值5000、SD写入83885字节、drop=0、err=0。见 `local/cache/zephyr-preflight-hardware/20260906/reconnect-uart8-2.log`。
- 同一串口输出中夹有 Horco CMSIS-DAP V2 Release 0.2 启动信息。暂未证明是调试器复位、打开接口输出信息或缓存内容，不能据此断定供电故障。
- 没有发现其他 Python、OpenOCD、Keil 调试进程占用；Windows显示DAP和COM6状态正常。
- 通过逐项初始化调试端口可读到 DP ID `0x6ba02477`，AP0/AP1 ID `0x84770001`，AP2 ID `0x54770002`；经 AP2 读取 H723 DBGMCU ID 为 `0x10016483`。说明SWD至少能完成这些真实芯片寄存器访问。
- DBGMCU CR 初值 `0x3`，对应固件开启D1睡眠/停止调试保持。当地 pyOCD 0.44.1 的 H723连接代码说明普通attach在部分低功耗状态下可能失败，并使用复位时接管流程。
- 复位时接管失败的准确位置：`target_STM32H723xx.py:151` 的 `assert self.dp.is_reset_asserted()`。工具没有确认复位线被拉低，不能把这次失败解释为主控已经损坏。
- 曾经依pyOCD目标脚本临时写CR为 `0x70003f`。进一步核对STM32H723芯片头文件后，发现D3保持位实际在7/8，而3/4/5为该型号未定义位；已清除3/4/5，改为 `0x700187` 并读回确认。没有修改Flash或选项字节。
- 改CR后仍未恢复可靠内存访问。AP0曾读到Flash首字 `0x24022a00`，随后外设和处理器调试寄存器访问出现WAIT/FAULT。AP1尝试也失败。**不能把调试保持设置缺项当成已证明的唯一根因。**
- 结束前已显式发送释放复位请求，但未取得主控暂停、加热关闭的读回证据。没有继续启动加热测试。

助手命令纠错：前面一次用到了不适用于H723的DBG地址 `0xe0042000`；另一次 `read32 ... 2` 把字节数误当成字数，引发对齐错误。后来改用H723实际地址和4字节对齐长度后仍有独立的访问失败；不能用那两次参数错误诊断硬件。
