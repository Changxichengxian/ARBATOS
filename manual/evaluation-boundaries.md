# 评分边界

这页用来说明以后评价 ARBATOS 仓库时哪些算代码架构问题，哪些属于实车硬件和发布过程的边界。

## SD 发布纪律

SD 日志启动时会写 `SDLOG_TAG_BUILD_INFO`。这条记录包含：

- `target`
- `board`
- 16 位 `git_sha`
- `build_dirty`
- `build_date`
- `build_time`
- `config_crc32`
- `schema_version`
- 任务、设备和运行时计数字段

Keil 工程的 `BeforeMake` 和 `tools/build.ps1 -Action gcc` / `tools/build.ps1 -Action gcc-build` 都会先刷新 `shared/generated/build_info_autogen.h`。这个生成文件不进 Git，但会被固件编进 SD 日志。

评价发布纪律时，重点看上车日志能不能把固件身份说清楚：目标、板子、16 位 Git 编号、dirty 标记、构建时间和配置 CRC 都能从日志里解析出来，就说明这次固件有基本追溯链路。`build_dirty = 1` 不是代码架构缺陷，它是在说明这次二进制包含未提交改动；复盘时需要把这个事实写清楚，但不能再按“没有发布纪律”重复扣分。

这件事必要，是因为嵌入式问题经常只能靠上车日志复盘。没有固件身份，后来看到的电机掉线、配置变化或控制异常，很容易对不上当时实际烧进去的代码和参数。

## CAN 和实车硬件边界

CAN 丢包、线束质量、端接、电源噪声、总线负载余量、电机选型和机械空间，属于实车集成风险。当前车上即使存在丢包，只要系统还能用，不能把这些物理限制直接算成代码仓库架构扣分。

评价代码架构时，只看仓库有没有把代码该负责的部分做好：

- CAN 总线、ID、协议和电机模型是否有清晰配置。
- 收发路径是否集中，控制任务是否避免直接拼裸 CAN 帧。
- 在线检测、错误计数、超时状态和安全输出是否可见。
- SD 日志、`g_watch` 和调试工具是否能复盘问题。
- 构建和检查路线是否能证明代码在当前目标上还能编译。

如果以后发现的是 CAN 配置错误、协议解析错误、发送队列设计问题、没有故障计数、没有安全状态、日志无法复盘，那仍然算代码问题。只有由实车硬件条件造成的丢包和体验上限，才不按仓库架构扣分。
