# 调试与日志

按“确认反馈 → 单轴动作 → 调参数 → 联动 → 留日志”的顺序使用。编译和下载步骤见[CLion 开发指南](CLion开发指南.md)。

- [上车检查](#上车检查)
- [控制参数调试](#控制参数调试)
- [日志与复盘](#日志与复盘)

## 上车检查

这份清单用于第一次上车、换硬件、改控制链、改电机装配、改输入映射之后。不要跳过“无动力”和“反馈确认”阶段。

### 0. 上车前准备

- [ ] 确认当前代码分支、commit、是否 dirty。
- [ ] `tools/build.ps1 -Action check -Project <TARGET>` 通过，并且对应 Zephyr 目标从干净目录构建通过。
- [ ] SD 卡可写，插卡后能生成新日志。
- [ ] 遥控器安全档位置确认。
- [ ] 摩擦轮、拨盘、底盘、云台能单独断电或物理卸载。
- [ ] 底盘架空，车轮离地。
- [ ] 现场有人能立刻断电。

当前构建不会自动刷新 Git 身份。按 [日志说明](调试与日志.md#日志与复盘) 在构建前运行 `GenBuildInfo.ps1`，并留存实际固件和哈希；`build_dirty = 1` 时记录具体未提交改动。

### 1. 无动力确认

先不接高功率负载，至少确认：

- [ ] 状态灯有变化，不是卡死。
- [ ] `g_watch` 能看到任务计数在动。
- [ ] 遥控输入源在线，语义轴和开关变化正确。
- [ ] `SdLogGetStats()` 能看到日志 active，丢包为 0 或可解释。
- [ ] `RtProf` 没有明显超预算。

此时不看“手感”，只确认程序在跑、输入能进来、日志能留住。

### 2. IMU 检查

- [ ] 温控能到目标温度并稳定。
- [ ] 静止时 gyro 接近 0。
- [ ] 轻轻转动车体时 yaw / pitch / roll 方向符合预期。
- [ ] 姿态没有明显跳变。
- [ ] 校准读取与保存路径明确：M 板 Flash 保存仅在专用准备模式开放，正式固件只读；A/C 板持久校准尚未完成。

IMU 不可信时，不继续调云台、底盘和轮腿。轮腿尤其不要在 IMU 不可信时给站立或平衡输出。

### 3. CAN 反馈检查

先确认反馈，再给输出。

- [ ] CAN 收发计数不是全 0。
- [ ] 每个电机在线状态正确。
- [ ] 手转电机时速度方向符合预期。
- [ ] CAN ID、反馈 ID、总线号、协议类型和电机型号对应。
- [ ] 不用的轴没有被误判在线，也不会收到输出。

反馈不稳定时先查线、终端电阻、ID、总线和协议，不要急着调 PID。

### 4. 单子系统动作

推荐顺序：

1. IMU 和输入。
2. 云台 yaw 单轴。
3. 云台 pitch 或第二 yaw 轴。
4. 底盘低速。
5. 摩擦轮。
6. 拨盘。
7. 裁判、视觉、日志、遥测。
8. 轮腿或机械臂实验。

每一步都用低限幅、小输出、短时间动作。确认以下内容后再提高输出：

- [ ] 正方向正确。
- [ ] 反馈方向正确。
- [ ] 限位正确。
- [ ] 遥控安全档能停。
- [ ] 断输入或失联能停。
- [ ] SD 日志里能看到命令、反馈和状态。

### 5. 轮腿 / MIT 电机额外检查

MIT 轮腿或达妙 MIT 模式不要直接进平衡实验。先按这个顺序：

- [ ] 单电机反馈在线。
- [ ] 使能 / 失能帧确认有效。
- [ ] 状态反馈能确认 enabled / disabled / fault。
- [ ] 单关节小幅位置或力矩动作。
- [ ] 单腿离地动作。
- [ ] 板凳模型或架空模型。
- [ ] 最后再做落地站立和平衡。

任何时候出现无反馈、IMU 不可信、腿长异常、遥控安全档、急停，都应该清零输出或进入安全阻尼。

每步记录电机型号和固件、ID/master ID、CAN 总线与波特率、反馈 ID、接线与终端电阻、控制模式、限幅、参数来源、使能/反馈状态、异常和退出结果；日志与对应固件一起保存。不能用旧 C 板记录代替 M 板实测。

### 6. 收尾

- 每次测试按下文的[日志与复盘](#日志与复盘)保存固件、参数、动作和结果。
- 把有效参数改回 `Robotconfig/<TARGET>/Config*.inc`，重新编译，确认参数没有只停留在 RAM 临时值。
- 发现代码问题时，先留日志和复现步骤，再修改；当前接线与限制写回相应车型或开发板说明。

## 控制参数调试

PID 调试的前提是反馈可信、方向正确、限幅安全。反馈没确认之前，不要调 PID。

### 基本顺序

1. 先确认电机反馈和控制输出方向。
2. 先调内环，再调外环。
3. 先单轴，再多轴。
4. 先低限幅，再提高限幅。
5. 每次只改一两个参数，并记录效果。

常见双环顺序：

- 云台：速度环 -> 角度环。
- 底盘：单轮速度环 -> 运动学合成 -> 跟随环。
- 射击：摩擦轮速度 -> 拨盘控制。
- 轮腿：单关节 / 单腿 -> 模型参数 -> 平衡控制。

### 先做的安全限制

调 PID 前先把这些限制调保守：

- 最大电流 / 最大力矩。
- 目标速度和目标角度变化率。
- 软限位。
- 遥控安全档。
- 失联保护。
- 运行编排只放行当前要调的子系统。

如果一个参数会让车突然大动作，先不要通过 AUX 临时调参直接大步改。

### 数据入口

| 入口 | 用途 |
|---|---|
| `g_watch` | 快速看在线状态、命令、反馈、错误码 |
| AUX 遥测 | 看少量实时曲线，适合边调边看 |
| SD 日志 | 复盘长时间动作、超时、掉线、限幅原因 |
| `tools/PidAutotune/` | 辅助单环整定，不替代人判断 |
| `RtProf` | 看控制周期是否被日志或通信拖慢 |

调参时至少要能看到：目标值、反馈值、输出值、误差、限幅状态。

### 手动调参建议

#### P

P 决定当前误差给多少输出。

- 反应太慢：逐步加 P。
- 开始振荡：P 太大，或者反馈延迟 / 摩擦 / 限幅已经影响闭环。
- 方向一错就发散：不要调 P，先修方向。

#### I

I 用来消除稳态误差。

- 长时间差一点到不了目标：小幅加 I。
- 低频来回晃：I 可能太大。
- 输出经常顶限幅：先处理限幅和目标，不要靠 I 硬顶。

#### D

D 用来抑制变化，但也会放大噪声。

- 高速接近目标时容易过冲：可以少量加 D。
- 反馈噪声大：先滤波或降低 D。
- 云台 gyro 反馈已经比较直接时，不要盲目加很大的 D。

### 云台

建议顺序：

1. 只开 yaw 或 pitch 单轴。
2. 先确认编码器 / gyro 方向。
3. 调速度环，让速度命令和反馈能跟上。
4. 调角度环，让角度目标不过冲。
5. 加回软限位、运行编排、输入映射。
6. 最后再看视觉、裁判、射击联动。

双 yaw 云台先把下 yaw 调稳，再接上第二 yaw。第二 yaw 的方向、限幅和输出符号要单独确认。

### 底盘

建议顺序：

1. 单个轮子低速输出，确认方向。
2. 四轮分别低速，确认装配顺序。
3. 调单轮速度环。
4. 低速平移和旋转。
5. 再调跟随环。
6. 最后接功率限制和裁判数据。

底盘抖动不一定是 PID 问题，也可能是轮子方向、轮距参数、反馈 ID、底盘坐标系或功率限制在打架。

### 射击

摩擦轮和拨盘分开调。

- 摩擦轮先看速度反馈和启动电流。
- 拨盘先低速空载，确认方向和卡弹保护。
- 有弹测试时先低频，确认热量、裁判数据和卡弹处理。

不要在拨盘反馈和卡弹保护不清楚时直接追求射频。

### 轮腿 / MIT

轮腿调参必须分阶段：

1. 单电机 MIT 模式。
2. 单关节小动作。
3. 单腿离地。
4. 双腿架空。
5. 板凳模型。
6. 落地站立。
7. 平衡和移动。

每个阶段都要留日志。重点看模式、腿长、腿角、关节力矩、轮力矩、IMU 状态、限幅原因和失联保护。

每次调参记录子系统、运行模式、修改参数、动作、现象及下一步；和对应 SD 日志一起保存，使用下文统一模板。

## 日志与复盘

SD 日志的目标不是“把所有东西都写下来”，而是让一次上车能被复盘：这版固件是谁编的、用的什么配置、跑了哪些状态、什么时候掉线或超时。

### 当前格式

当前主线只保留一种 SD 日志格式：

- 文件头：`sdlog_file_header_t`
- 数据块：`sdlog_block_header_t + block bytes`
- 块内容：变长整数记录流
- 记录：`dt_ms + tag + len + payload`

旧的 v1 / v2 / v3 命名已经删掉，不再为了没实测过的格式保留解析分支。文件头也不再写数字格式版本。

如果 payload 自身需要演进，按 tag 规则处理：

- 兼容新增字段：追加字段。
- 不兼容改字段：提升 payload version，或者分配新 tag。
- 不要复用同一个 tag 表示两种不兼容结构。

### 固件身份（BUILD_INFO）

每个日志启动时会写 `SDLOG_TAG_BUILD_INFO`。解析后能看到：

- `target`
- `board`
- `git_sha`
- `build_dirty`
- `build_date`
- `build_time`
- `schema_version`
- `config_size`
- `config_crc32`
- `task_module_count`
- `task_module_mask`
- `high_rate_div`
- `compression_enabled`

当前 Zephyr 的 CMake 和 `tools/build.ps1` **不会自动刷新 Git 构建身份**。需要这份信息时，在构建前手动运行：

```powershell
pwsh -NoProfile -File .\tools\GenBuildInfo.ps1
pwsh -NoProfile -File .\tools\build.ps1 -Project HERO-M
```

脚本生成 `shared/generated/build_info_autogen.h`，保存 16 位 Git 编号、已跟踪文件的工作区/暂存区改动标记及生成时间。该文件不提交 Git；`SdLog.c` 在文件存在时读取它。脚本运行后再改代码会使身份过期；遗留的本机生成文件也可能对应旧提交。

因此日志存在 `BUILD_INFO` 不等于已准确标识当前固件。上车时同时留存实际 ELF/BIN、哈希、Git 状态与配置，检查日志身份是否一致。`build_dirty = 1` 表示生成信息时有已跟踪文件改动，需要记录具体差异。

### 重启证据的限制

日志支持 `RESET_EVIDENCE` 记录结构，但当前 Zephyr `BspResetEvidence.c` 只使用普通静态 SRAM，启动时清空。它不提供跨重启证据，也不能保证取得上次 RCC 复位标志或 CPU 异常栈。旧 HAL 备份 SRAM 的保留、同步后确认等保证不适用于当前实现。

### 查看日志

启动网页查看器：

```powershell
python tools\sdlog\SdLogViewer.py sdlog_0001.bin
```

常用导出：

- 单个 tag CSV：网页里的 `Export tag CSV`
- 单个字段 CSV：网页里的 `Export field CSV`
- 未知记录 CSV：网页里的 `Export unknown CSV`

未知记录 CSV 会保留：

- tick
- tag
- payload 长度
- payload CRC32
- payload 十六进制内容

这保证解析器没跟上新 tag 时，原始数据不会直接丢。

### 解压日志

如果固件开启 LZ4 块压缩，可以先解压成当前格式的未压缩文件：

```powershell
python tools\sdlog\SdLogDecompress.py sdlog_0001.bin
```

默认输出：

```text
sdlog_0001.bin.uncompressed.bin
```

这个脚本只去掉块压缩，不会转换成旧格式。

### 留基线日志

每个真正上车的阶段都应该留一组基线。推荐目录：

```text
local/logs/sdlog/<TARGET>/<YYYY-MM-DD>/
```

最少留这些信息：

```text
车型（Target）：
开发板（Board）：
Git 提交：
未提交改动（dirty）：
电池：
硬件改动：
测试动作：
子系统与运行模式：
参数改动：
日志文件：
现象：
结论：
下一步：
```

推荐至少覆盖：

- 启动后静止 10 秒。
- 遥控输入变化。
- 云台单轴动作。
- 底盘低速动作。
- CAN 反馈在线 / 掉线情况。
- `RT_PROFILER` 和 `SYS_STATS`。
- 轮腿实验时的 MIT 配置和状态。

只有 `META` 或只有 `BUILD_INFO` 的文件不能当运行基线，它只能证明文件创建成功。

### 新增日志记录前检查

新增 SD 日志 tag 前先问：

1. 这个数据是否真的需要高频记录？
2. 能不能降频或打包成 base stream？
3. payload 里字段单位是否清楚？
4. 解析器是否同步更新？
5. 有没有样例日志或合成测试能覆盖？

高频控制任务里新增日志时，还要考虑复制成本、环形缓冲占用和最坏耗时。日志不是直接写文件，但仍然会复制数据并进入短临界区。
