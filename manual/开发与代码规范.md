## 程序运行结构

ARBATOS 由开发板支持、车型配置、共享控制逻辑和工程入口组成。调度保持静态，设备、电机、控制器使用固定容量的配置与实例表；当前仍保留业务任务和兼容接口。

### 启动和任务

`projects/src/main.c` 进入 Zephyr 应用，`ArbatosTarget.c` 选择车型，`ArbatosRuntime.c` 完成运行初始化和任务创建。旧业务代码通过 `shared/zephyr/compat/` 使用任务、延时等兼容接口，实际由 Zephyr 调度。

任务信息分成两处，各自只维护一次：`RobotTaskCatalog.def` 定义任务编号、名字、入口、默认优先级、默认栈和依赖；`Robotconfig/<车型>/RobotConfig.toml` 选择本车任务并可覆盖栈或优先级。生成的任务表同时供 `ArbatosRuntime.c` 创建线程和 `g_config.profile.task_modules` 使用，不能直接编辑生成文件。

`ArbatosRuntime.c` 用生成任务表分配固定栈、创建任务并注册模块，再调用 `AppCreateEnabledModuleTasks()`。新增任务只补任务目录和实现，不在运行入口重复写一遍。

模块声明中的周期、预算、资源和默认栈用于描述与观察，尚未全面替代实际任务创建参数。Zephyr 专用服务及准备/接收/音乐测试模式也有独立启动分支，不能只用车型任务表推断所有线程。

### 输入、控制和输出

```text
DBUS/SBUS、ELRS/CRSF、图传遥控等
  → ManualInput → ControlInput → 控制任务 / 控制器
  → LowCmd → CAN / RS485 发送适配、PWM 发送适配 → 执行器

CAN 中断 → 接收队列 → CanRxTask → CanReceive / MotorInst
  → 状态快照、控制任务、Watch、SD 日志
```

控制任务写语义命令或已绑定执行器命令，协议层处理电机型号、总线、ID、帧格式和发送限额。高频循环优先读取缓存或快照，初始化时把设备名解析成 ID，避免反复查询整份配置。

CAN、RS485 和 PWM 共用 `ControlMgr` 控制许可及 `LowCmd` 命令发布。CAN/RS485 由 `CanTxTask` 消费实际电机路由；普通 PWM 舵机在现有 `ServoControlTask` 内发布并消费位置命令，无需增加线程，写寄存器前原子检查最新控制权。PWM 槽的 `PosVel.q` 是 [-1,1] 归一化位置、0 为中点；它不代表 MIT 电机接口的弧度，物理角度还需要具体舵机行程标定。总线舵机留有 UART 传输类型，尚无通用报文驱动，必须按具体协议接入。

PWM 的 30 ms 命令有效期在舵机任务执行发送步骤时检查；该任务永久卡住时，没有另一个发送线程或定时器自动关闭它。M 板进入系统致命故障路径时会直接关闭 TIM1/TIM2 输出，不能把这项覆盖扩大解释为所有任务卡住都已被检测。

发送路径在绑定时缓存编号、能力和路由，批量查询逐轴禁写状态，发送循环只快照实际路由。RM 电机组在发帧前获取该组快照，不再先复制一次全部电机命令。命令发布时的控制权检查、过期处理、解锁后重新发布、真正入队前的撤销检查覆盖不同时间窗口，继续保留。

### 设备和控制器

- `g_config.devices` 描述设备实例，`RobotDeviceConfig.h` 统一读取；`g_config.motor.*` 仍承载具体电机参数。
- `MotorInstRefresh()` 依据配置建立电机实例。可用 `MotorInstFindByName()` 查询，再通过绑定 ID 发命令、读反馈。
- `ControlMgr` 管理控制域、注册、资源占用、切换、停止和故障状态。`ControlAlgorithm` 只负责算法计算；`ControlRuntime` 负责输入、反馈、安全边界和经 `LowCmd` 提交输出。
- 底盘、云台、射击等仍有各自任务循环和状态机；不能把已有控制器接口理解为所有调度已统一。
- 当前通用 `ControlRuntime` 只承接底盘、云台算法扩展，已有差速底盘和双轴转速云台示例；正式车型仍主要使用专用任务。迁移时需要逐项承接原机构的输入语义、功率或机械限幅、校准、故障恢复及日志，确认行为和周期预算后再切换，不能仅把旧任务循环放进算法 `step()`。
- `shoot.rm` 独立创建 `ShootControlTask`，只由该任务推进发射状态机；云台任务只发布机构状态，不直接调用发射步骤。发射周期读取 `g_config.shoot.control_period_ms`，不再借用云台周期。经典云台保留原有发射许可，通用云台读取有效控制命令确认运行许可，无云台组合仍保留输入与故障保护。
- 发射任务保留现有车型的 201 ms 启动等待；单任务调试必须明确选择 `SHOOT_RM`，再选择摩擦轮、拨弹或组合变体。配置了云台时仍保留云台许可检查，不因单任务调试绕过。通用云台与发射组合时，云台周期不得超过 20 ms 的许可有效期。
- `g_watch.runtime` 按任务、设备、电机、控制器和控制域提供观测；SD 启动记录包含配置和设备信息，固件身份的限制见 [日志说明](调试与日志.md#日志与复盘)。

经典云台的 `GimbalControlTask.c` 保留任务循环和旧接口入口。控制计算在 `GimbalControl.c`，输入与反馈快照在 `GimbalRuntime.c`，故障状态在 `GimbalFault.c`，输出提交与恢复清零确认在 `GimbalOutput.c`；双水平轴、日志、校准和调参分别由 `GimbalDualYaw.c`、`GimbalLog.c`、`GimbalCalibration.c`、`GimbalTune.c` 负责。这些文件分别编译，通过私有头中的显式上下文或状态参数协作，不再把实现文件直接包含进任务源文件。

轮腿、经典底盘及发送任务仍包含多个 `.inc` 实现片段；片段与主文件共用一个编译单元和内部状态，属于阅读分段，尚未形成同样的模块边界。小轮腿专用板凳控制已提取到 `WheelLegBench.c`，启停、反馈检查与输出提交仍接在轮腿任务流程中。后续整理优先明确状态归属和输入输出，不以片段数量作为模块化完成的依据。

完整 `g_watch` 镜像由车型 `features.watch_full` 控制，默认关闭；轻量版本保留启动阶段接口，核心故障记录继续走备份 SRAM。关闭时不创建只负责复制 Watch 的默认线程，控制摘要日志直接读取已有状态快照。SDLOG 未启用时编入空日志接口，取消日志环形缓存、压缩缓冲与日志任务；其他功能仍需要的 SD 文件系统照常保留。这些均为编译开关，桌面端修改后需重新构建。

未选轮腿或机械臂时不会创建对应控制任务，专用状态缓存由编译配置裁剪；通用电机表、命令表仍保留 18 个稳定编号。仅启用 SERVO 的车型增加 4 个 PWM 命令槽，普通车型不增加这部分预留。要进一步按本车执行器数量分配，需要统一固定编号与稠密索引的边界。客户端“内存与 Flash”展示实际链接结果，不把“源码参与编译”直接当作“占用了固件空间”。

经典四轮底盘通过 `power.limitMode` 选择限制策略，现有车型默认 `ChassisPowerLimitAuto`，保持裁判在线用模型、无有效裁判时用总指令的行为。`ChassisPowerLimitTotalCommand` 始终只约束四轮总指令；`ChassisPowerLimitModel` 离线按配置瓦数使用模型，在线还服从裁判功率和缓冲预算；`ChassisPowerLimitModelAndTotal` 先约束总指令，再按模型约束功率。轮腿控制器不读取这组参数。

`no_judge_total_current_limit=36000` 表示四轮指令绝对值之和，与安培/瓦特不同，是沿用的调试值。显式模型模式遇到不支持的电机时退回该上限；备用上限也无效时仅该底盘零输出。模型没有动态内存分配，主要成本来自四轴估算及限功率时的求根；具体耗时需单独测量，不能由整段底盘耗时反推。

新增硬件优先补设备与驱动，新增算法优先复用控制器和输入输出接口，新增机器人优先改车型配置。确需独立周期或栈时再添加任务模块。

### 故障和验证边界

当前有安全档、输入超时、离线检测、限幅、局部故障与输出锁等保护，具体动作仍由对应控制任务和协议实现决定。实车必须逐项验证断输入、断反馈、异常恢复及停机行为。

H723 的 Zephyr 致命异常、断言、栈检查失败和运行期 NMI 已接入 `RobotFaultZephyr.c`：关闭中断和 PWM，保存异常摘要，依据预先生成并带校验的执行器路由尝试 CAN/RS485 停机，然后复位。异常路径使用芯片寄存器和有限轮询，不调用 SD、普通驱动锁或动态内存。CAN 总线关闭、时钟故障、执行器掉线时停机帧可能发不出去；已经开始发送的旧帧也无法撤回，实车仍要验证独立断能措施。

`BspResetEvidence.c` 使用备份 SRAM，早期启动先读取 RCC 复位标志及带校验的故障摘要。发现未保存故障时，本次启动锁住 CAN/RS485 和舵机输出，继续运行接收与日志任务；SD 同步成功后才清除备份记录，输出锁保持到下一次人工重启。没有 SD 或写入失败时保留证据和锁。备份域失去供电可能丢失记录，不能把它理解为任意断电后永久保存。字段与验收步骤见[调试与日志](调试与日志.md#异常停机与重启记录)。

CAN 异常需区分配置、解析、队列、任务延时、调试暂停、总线负载和物理接线。仅凭丢帧计数不能断定硬件或软件根因。电脑上的检查与逻辑测试可验证部分代码行为，实际总线、温升、机械动作和断能效果需实物确认。

HERO-M 已有整车运动实测；MINIWHEELEG-M 于 2026-10-27 确认专用板凳配置下的 90 mm 固定短腿原地平衡，具体条件见[车型安装说明](../Robotconfig/MINIWHEELEG-M/安装说明.md#2026-10-27-独立板凳调平记录)。其他动作、外设、长期负载和致命故障停机仍需分别验收。A/C 板已开放经典底盘、单云台、RM 射击及对应服务，当前能力与缺项见[开发板说明](../boards/README.md)。

## 新增任务

ARBATOS 这里的模块，只覆盖机器人下位机常见模块：输入、通信、IMU、底盘、轮腿、云台、机械臂、日志、诊断和启动服务。它暂时不追求传感器项目、遥控器项目或非机器人项目的通用性。

### 模块要说清楚什么

每个任务模块都在 `shared/application/robot/RobotTaskCatalog.def` 登记，`RobotModule.h` 从中生成描述：

- `name`：模块自己的名字，例如 `module.classic_chassis`。
- `taskName`：对应旧任务名，例如 `task.classic_chassis`，用于兼容现有任务创建和调试视图。
- `kind`：模块类型，例如 input、comm、device、service、control、safety。
- `defaultPeriodMs` / `defaultBudgetUs`：默认周期和时间预算；运行时可由 `RobotModulePeriodMs()` 读到目标配置里的实际周期。
- `defaultStackWords` / `defaultPriority`：默认栈和优先级，车型覆盖值参与生成实际线程创建参数，描述与运行使用同一份值。
- `requires`：模块依赖哪些资源，例如 `RobotResourceLowCmd`、`RobotResourceCan1`、`RobotResourceImu`。
- `provides`：模块提供什么能力，例如 `RobotResourceChassisOutput`、`RobotResourceMotorFeedback`。

### 新增模块流程

1. 若只是新增底盘或云台算法，按 [控制器说明](../shared/controllers/README.md) 新建算法目录，复用通用任务，不增加任务枚举。
2. 确实需要独立线程时，在 `RobotTaskCatalog.def` 增加一条：稳定编号、名字、入口、默认栈、优先级、任务依赖及实现源。按需要在 `RobotModule.h` 定义资源说明；已有资源组可直接复用。
3. 车型在 `RobotConfig.toml` 选择服务或控制器。枚举、任务名表、profile 和启动表自动生成，保持单一来源。
4. 运行配置检查和针对该任务的回归，再编译目标固件。生成器会拒绝未知任务、依赖循环、输出冲突、未登记实现和不合理的栈/优先级；具体驱动行为仍需相应测试。

### 当前边界

现阶段模块声明用于运行时描述与 Watch 观察。它会把模块类型、周期、预算、栈、优先级、依赖数量和产出数量放进 `g_watch.runtime.task_module[]`，方便实车观察。

任务创建仍通过 `AppTaskBootstrap.h`。查看构建目录的 `robot-config.json` 可核对栈、优先级与依赖；`CheckZephyr.py` 会先执行生成器的声明检查，但不代替时序和实车验证。

## 代码规范

这份规则只服务 ARBATOS。命名整体用英文，但要让中文母语的人读起来轻松；注释主要用中文，解释意图、边界和实车约束。

### 核心口径

`LowCmd` 这类名字是本仓库以后要靠近的风格：

- 模块名短，例如 `LowCmd`、`MotorInst`、`ControlMgr`、`RtProf`、`SdLog`。
- 公共函数写成“模块名 + 动作”，例如 `LowCmdSetCurrent()`、`MotorInstFindByName()`。
- 类型名用短英文名，不再新增 `_t`、`_e` 后缀。
- 普通结构体字段优先用 `lowerCamel`，例如 `lastRxTick`、`cmdCaps`。
- 宏、编译开关和日志 tag 仍然用全大写，因为它们需要一眼看出是常量或协议值。

不要再新增这种句子式名字：

```c
motor_instance_set_current_ids_best_effort();
control_manager_switch_to_named_control();
rt_profiler_get_runtime_summary();
```

优先写成：

```c
MotorInstSetCurrentIdsBestEffort();
ControlMgrSwitchByName();
RtProfGetSummary();
```

### 命名规则

- 文件名按模块命名，公共模块优先用 `MotorInst.c`、`RtProf.h` 这种短英文名。
- 公共函数使用 `ModuleActionObject()`，动作放前面，宾语尽量短。
- 文件内私有函数可以继续用小写风格，但不要写很长的下划线句子。
- 变量名能短就短，但不能靠猜；`id`、`bus`、`tick`、`cmd`、`fb` 这类上下文明确的短名可以用。
- 跨模块可见的名字必须带模块名，避免 `init()`、`update()`、`get()` 这种泛名飘到全局。
- 协议字段、寄存器名、厂商库 API 和外部文件格式字段按原始资料保留，不强行改成项目风格。

### 注释规则

新增注释主要用中文。下面这些情况可以保留英文：

- SPDX、许可证、版权和第三方文件头。
- 协议字段、寄存器名、CAN ID、库函数名、工具命令和外部标准名。
- 和厂商手册、数据手册完全对应的原文术语。

注释写“为什么”和“边界”，少写“这一行做了什么”。推荐写：

- 模块入口前的阅读地图。
- 实车约束：总线负载、电源、机械限位、启动顺序、调试前提。
- 不明显的安全策略：失联后的输出、限幅理由、故障保持时间。
- 兼容性原因：为了旧日志、旧配置、厂商库或系统适配差异保留的代码。

不推荐写：

- 把函数名逐字翻译一遍的注释。
- 已经过期的调试记录。
- 和代码行为不一致的历史描述。
- 大段英文解释但没有中文结论。

### 排版

- 新文件默认 4 空格缩进，不使用制表符缩进。
- 已有文件按当前文件缩进和括号风格，不做无关格式化。
- 新 C/C++ 文件默认函数左大括号另起一行，控制语句左大括号跟随语句。
- 一行只写一条语句。
- 一行尽量不超过 120 个字符；超过时按语义换行。
- `if`、`for`、`while`、`switch` 即使只有一行，也优先写大括号。

### 头文件和宏

- 头文件应当自包含，单独包含也能通过编译。
- 头文件只放接口、类型、常量和必要宏，不放普通全局变量定义。
- 对外接口放在头文件，文件内辅助函数放在 `.c` 里并声明为 `static`。
- 多处使用的数字必须命名成宏、枚举或 `const`，单点使用但含义不明显的数字要写注释。
- 函数式宏的参数和整体表达式要加括号。
- 多语句宏使用 `do { ... } while (0)`。
- 复杂逻辑优先使用 `static inline` 或普通函数，少把流程藏进宏里。

### 旧代码处理

旧代码风格不统一不单独扣分。真正要扣分的是继续扩大混乱：新改动沿用很长的下划线句子、注释语言混杂、命名没有模块边界、或者把行为改动埋在大范围格式化里。

以后改旧代码按这个顺序处理：

1. 先保证行为正确、能编译、能检查。
2. 再把本次触碰到的公共接口和注释改清楚。
3. 最后只在必要时做小范围风格整理。

如果要统一整个模块，单独做一次改名提交，提交说明写清楚不改变行为。

### 配置和日志名称

`task.*` 模块字符串、配置键、AUX 参数名、SDLog tag、payload 字段和 CSV 列名属于数据接口。不要为了统一代码风格直接改名。兼容扩展优先追加字段，不兼容修改需新 tag 或版本，并同步更新解析器、样例和文档，保证旧日志仍可复盘。

### 文档命名与维护

- 自写说明文档的文件名和标题用中文，例如 `调试与日志.md`、`安装说明.md`；CLion、Zephyr、CAN、USB 等工具或协议名称保留。
- 保留 `README.md`、`AGENTS.md`、GitHub 自动识别的模板文件名，以及第三方许可证的原名。
- 同一用途维护一份说明，用章节组织；不要再为入口导航、一次整理或一段验证过程单独增加文档。
- 修改接口或路径时同步更新相关说明和链接。实测结论写明日期、硬件、固件与未验证范围。
- 移动源码后同步检查 `#include` 和 CMake 显式源码清单，运行 `tools/build.ps1 -Action check`，并编译受影响目标；移动本地缓存时同步修改工具的默认输出目录。
