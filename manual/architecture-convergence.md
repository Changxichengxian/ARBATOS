# 架构收束与分阶段验收

这份文档把 ARBATOS 从“新旧运行方式并存”收束为单一机器人运行层的工作拆成可独立验证、可独立回退的提交。
每个阶段都必须保持现有目标可编译；控制行为发生变化时，优先由 `SENTINEL-M` 留一份实车或台架基线，再进入下一阶段。

## 最终边界

1. 高频控制只做固定数组、预绑定编号和有界复制，不在循环里扫描字符串、动态创建对象或执行阻塞 I/O。
2. 控制器通过类型明确的输入和状态快照读取数据，通过 `LowCmd` 写执行器，不直接拼传输帧。
3. `ControlMgr` 是控制器生命周期、资源占用和调度入口，不再只充当旧任务的运行许可开关。
4. 目标只维护一份模块声明；编译开关、任务创建、周期、栈、优先级、预算和观察表由它生成或严格校验。
5. 普通设备故障默认只影响自身或所属功能；只有显式声明的强耦合组才执行组内停机。
6. 跨任务数据带发布序号和时间戳；控制器能判断数据是否一致、是否过旧。
7. `components` 不依赖车型配置、板级入口和 RTOS；板级驱动不依赖具体控制任务、Watch 或日志实现。
8. 每个纯控制核心、协议解析和故障策略都能在主机运行测试；持续检查同时覆盖静态检查和 GCC 构建。

## 故障影响范围

| 级别 | 典型情况 | 固件动作 | 恢复条件 |
| --- | --- | --- | --- |
| 单设备 | 普通底盘轮、单个云台轴、拨弹或摩擦轮掉线 | 只清该设备输出，其他无机械强耦合功能继续运行 | 设备连续健康并满足本功能的安全输入 |
| 强耦合域 | 轮腿六电机、关键姿态反馈或轮腿控制核心异常 | 原子清除该域全部输出并重置控制状态，不影响云台、射击和通信 | 全体成员连续健康，操作者回到安全输入后再重新使能 |
| 系统致命 | 栈溢出、内存分配失败、CPU 异常、启动硬件失败 | 立即发送全局安全帧，记录原因并复位 | 只能由系统重新启动 |

故障动作由显式策略决定，不能根据检测项优先级偷偷扩大范围。新增设备没有声明强耦合关系时，默认采用单设备隔离。

当前已明确的功能策略如下：

- 轮腿的六个执行电机、姿态输入和控制配置属于同一个强耦合域，任一关键成员异常都保持六轴局部禁写；恢复必须连续健康、输入回安全位，并从下一完整控制周期重新接管。
- 发射域中，拨弹轴掉线只隔离拨弹，摩擦轮仍可预热；任一实际配置的摩擦轮异常会停止整个发射域，但不会停止云台、底盘、通信或其它任务。
- 云台、经典底盘和机械臂普通电机按轴隔离。云台随动状态超过 20 ms 未更新时，底盘退化为无随动，仍保留平移和手动转向。
- `GIMBAL_YAW_ONLY` 明确表示俯仰轴不参与当前控制和瞄准就绪条件，因此俯仰掉线不会阻止固定俯仰方式射击；正常和双 yaw 变体仍要求当前控制 yaw、pitch 与 IMU 都健康。
- 普通轴恢复前要连续健康 200 ms，并要求对应操作输入回到安全位；恢复帧先清控制状态和命令，再释放禁写，下一完整控制帧才重新接管。

局部停止不能只写一次零值。故障域会在 `LowCmd` 中持有逐电机禁写权，低优先级控制、调试和主机命令在恢复前都不能重新接管；发送任务在使用缓存命令时也必须再次服从该禁写状态。RM 分组帧的最终复核和非阻塞入队按同一临界区排序，MIT 与 Unitree 在协议发送前再次复核；机械臂任务只发布 `LowCmd`，不再和发送任务同时直发协议帧。

`FaultMgr` 保持每个控制任务独立、无锁和固定容量；当前最大域是轮腿的八个成员，因此默认只预留 8 个设备、2 个域，单实例约 348 B，避免为普通三四轴功能复制 32 设备的大表。

## 分阶段提交

当前进度以 Git 历史为准；每一阶段独立提交，后续阶段不得把前一阶段的行为修正混回同一个提交。

### 一、实时数据通道和热点

- 缩短 `LowCmd`、状态快照和日志等高频临界区。
- CAN 多总线公平取帧。
- 栈余量等昂贵诊断移出高频周期。
- IMU 以完整快照发布，关键控制器不再混读相邻采样周期。
- 增加重试、丢弃、数据年龄和兜底计数，方便实车判断收益。

经典底盘进一步把云台状态和四轮反馈收成单帧输入：云台状态每周期只读取一次；四轮通过一次批量 `LowState` 复制取得反馈，再由同一份 `MotorState` 同时完成健康判定、PID、功率估算、状态和遥测。控制层不再保留指向 CAN 接收区的电机测量指针。`lastEcd` 使用 `MotorState` 原有的对齐空位保存，结构体大小不变；RS485 驱动只在接收计数前进时更新上一编码器值。

单帧快照曾把经典底盘任务的最坏静态栈深暴露到 2800 B，而旧配置只有 2048 B。现在普通帧和安全帧各自只保留一份局部快照，初始化阶段不再提前抓取快照；F4/F427 目标的经典底盘栈为 768 words（3072 B），实际启用经典底盘的 H7 目标通过 `BoardFreertos.c` 使用 1024 words（4096 B）。H7 工程目录里仍保留另一份未参与最终镜像的任务入口，这种重复配置必须在单一目标描述阶段消除。加固 `ControlMgr` 后，Keil 不会自动展开的函数指针链按同时存活栈帧保守补全：HERO-C、HERO-M 和 SENTINEL-M 为 2312 B，CARRIER-A 与 INFANTRY-A 为 2240 B；F4/F427 最少剩余 760 B，两个 H7 目标均剩余 1784 B。后续扩展快照、控制门面或日志链路时必须继续检查调用图和运行期高水位，不能只凭任务入口的局部变量估算。

### 二、故障域和降级策略

- 建立设备故障、控制器故障和致命系统故障三类边界。
- 普通电机默认单点隔离；轮腿六电机和关键姿态反馈组成强耦合组。
- 故障动作、影响范围、恢复条件进入声明和主机测试。

### 三、控制器样板

- 先迁移一个边界清晰的控制域，让 `enter/update/stop` 真正运行控制逻辑。
- 输入只读快照，输出只写 `LowCmd`，日志只观察公开状态。
- 去掉旧任务对该控制域的隐式调用，形成后续迁移模板。

首个样板选择发射域。`ShootCtrl` 是任务、`ControlMgr` 和旧发射算法之间的唯一入口：启动阶段只登记并提出切换请求，等云台任务准备完成后，第一次真实控制帧才依次执行 `enter` 和一次 `update`。临时禁止输出通过同一 `update` 传入强制安全标志，控制域保持活动但每帧持续清零；显式停止才执行 `stop` 并释放活动状态。旧发射算法的初始化、步进和停止入口改为门面内部接口，任务和注册表不能绕过 `ShootCtrl` 直接调用。

### 四、控制体系合一

- 按样板迁移底盘、云台、射击、机械臂和轮腿。
- 高频任务可以继续独立存在，但只负责调度和 I/O 外壳，不再各自维护另一套资源与生命周期规则。
- 删除失去调用者的兼容入口和空弱实现。

经典底盘已经按样板接入 `ChassisCtrl`。任务每帧只调用一次门面，`ControlMgr` 的首次 `enter` 只完成绑定、PID 和故障管理初始化，随后同一帧执行一次 `update` 并抓取唯一反馈快照。遥控掉线和运行模式限制改为连续安全帧：底盘控制域保持活动，每帧仍更新反馈、故障分组、逐轴禁写和公开状态，只跳过 PID 与功率计算。正常 Runtime 只填写四路 `ChassisCtrlOutput`，任务在门面返回后统一写入 `LowCmd`；显式停止或管理层异常仍直接补写零命令，避免残留电流。

`ControlMgr` 的并发边界也由约定变成了可检查的状态：每个控制域共用一个更新占用标记，普通更新和按周期更新不能递归进入同一域；切换控制器时先在六个域之间原子检查并预留资源，旧控制器退出和新控制器进入失败都会释放预留。`Fault` 与 `EmergencyStop` 停机请求带明确优先级，普通切换、普通停止和清除 pending 都不能覆盖它们，回调内新增的急停会在新控制器执行 `update` 前处理。回调始终在临界区外运行，管理器公开注册、切换、资源冲突、更新重入和受保护请求拒绝诊断，Watch 只在原有运行时结构末尾追加诊断块，保留已有调试器字段布局。

手动输入先收束成一份 `ManualInputSnapshot`：原始输入、业务映射、活动来源、在线状态、来源掩码和三个序号按同一代发布，控制映射只在写者计算候选时执行一次。发布器使用双 bank 和读者固定计数，整块读取在临界区外完成；单写者在最终切换前同时核对输入 dirty generation 与两份配置，计算期间到达的新帧或热更新配置只能使旧候选作废。来源超时默认采用 100 ms，读取端即使遇到定时器守护任务停滞，也会把过期代压成原始与映射安全值；代级过期标记和来源 `update_seq` 失效共同阻止 32 位 tick 完整回绕后复活数十天前的命令。刷新工作区放在单写者静态存储中，ARMCC5 补全 FreeRTOS 间接回调后的最坏栈深为 360 B，所有目标 256 words 的定时器守护任务栈仍剩 664 B。旧舵机任务会在同一周期经过快照读取和运行生命周期检查，HERO-C 的静态最深栈为 344 B；其任务栈由 128 words 提到 192 words，给任务初始上下文和后续迁移留出余量。本提交为保证旧控制任务仍能使用 ELRS 和图传，暂时保留通用来源对 `DBUS_TOE` 的兼容更新；下一提交迁完所有在线状态消费者后，再把该检测入口收回到物理 DBUS 有效帧。

### 五、单一目标描述

- 一份目标声明决定模块、设备、任务和控制器组合。
- 生成或检查真实任务栈、优先级、周期、预算、资源和工程源文件。
- Watch、日志和仿真读取同一份声明，不再维护平行表格。

### 六、依赖边界

- 板级 IMU 只负责采样、原始坐标转换和硬件控制；融合、校准状态机和日志进入共享层。
- 为 `components`、`hal`、`boards`、`application` 增加可执行的依赖方向检查。
- 逐步减少直接包含 `main.h`、`RobotConfig.h` 和整块 `Watch.h` 的共享模块。

### 七、持续验证和性能基线

- 持续检查运行主机单元测试和全部 GCC 目标。
- 实车记录控制周期抖动、错过周期、数据年龄、最长临界区、CAN 队列峰值和端到端延迟。
- 性能预算以实测基线为准，仿真估算只作为提前预警。

## 每个提交的最低验证

- `tools/build.ps1 -Action check`
- `tools/build.ps1 -Action gcc-build -Project all`
- `SENTINEL-M` Keil：0 错误、0 警告
- `git diff --check`

涉及公共启动、配置生成、故障输出或编译清单的提交，还要重建全部七个 Keil 工程。

## 哨兵验证记录建议

每次烧写至少记录提交号、运行时长、遥控与上位机链路、CAN 收发失败数、控制周期最大值、栈余量、最小剩余堆和日志丢弃数。
如果某一版出现退化，先回到上一提交复现；不要把多个阶段一起烧写后再猜是哪一层引入的问题。
