# 架构收束与分阶段验收

这份文档把 ARBATOS 从“新旧运行方式并存”收束为单一机器人运行层的工作拆成可独立验证、可独立回退的提交。
每个阶段都必须保持现有目标可编译；控制行为发生变化时，优先由 `SENTINEL-M` 留一份实车或台架基线，再进入下一阶段。

## 最终边界

1. 高频控制只做固定数组、预绑定编号和有界复制，不在循环里扫描字符串、动态创建对象或执行阻塞 I/O。
2. 控制器通过类型明确的输入和状态快照读取数据，通过 `LowCmd` 写执行器，不直接拼传输帧。
3. `ControlMgr` 是控制器生命周期、资源占用和调度入口，不再只充当旧任务的运行许可开关。
4. 目标只维护一份模块声明；编译开关、任务创建、周期、栈、优先级、预算和观察表由它生成或严格校验。
5. 普通设备故障默认只影响自身或所属功能；只有显式声明的强耦合组才执行组内停机。
6. 跨任务数据带发布序号和时间戳；控制器能判断数据是否一致、是否过旧。
7. `components` 不依赖车型配置、板级入口和 RTOS；板级驱动不依赖具体控制任务、Watch 或日志实现。
8. 每个纯控制核心、协议解析和故障策略都能在主机运行测试；持续检查同时覆盖静态检查和 GCC 构建。

## 分阶段提交

当前进度以 Git 历史为准；每一阶段独立提交，后续阶段不得把前一阶段的行为修正混回同一个提交。

### 一、实时数据通道和热点

- 缩短 `LowCmd`、状态快照和日志等高频临界区。
- CAN 多总线公平取帧。
- 栈余量等昂贵诊断移出高频周期。
- IMU 以完整快照发布，关键控制器不再混读相邻采样周期。
- 增加重试、丢弃、数据年龄和兜底计数，方便实车判断收益。

### 二、故障域和降级策略

- 建立设备故障、控制器故障和致命系统故障三类边界。
- 普通电机默认单点隔离；轮腿六电机和关键姿态反馈组成强耦合组。
- 故障动作、影响范围、恢复条件进入声明和主机测试。

### 三、控制器样板

- 先迁移一个边界清晰的控制域，让 `enter/update/stop` 真正运行控制逻辑。
- 输入只读快照，输出只写 `LowCmd`，日志只观察公开状态。
- 去掉旧任务对该控制域的隐式调用，形成后续迁移模板。

### 四、控制体系合一

- 按样板迁移底盘、云台、射击、机械臂和轮腿。
- 高频任务可以继续独立存在，但只负责调度和 I/O 外壳，不再各自维护另一套资源与生命周期规则。
- 删除失去调用者的兼容入口和空弱实现。

### 五、单一目标描述

- 一份目标声明决定模块、设备、任务和控制器组合。
- 生成或检查真实任务栈、优先级、周期、预算、资源和工程源文件。
- Watch、日志和仿真读取同一份声明，不再维护平行表格。

### 六、依赖边界

- 板级 IMU 只负责采样、原始坐标转换和硬件控制；融合、校准状态机和日志进入共享层。
- 为 `components`、`hal`、`boards`、`application` 增加可执行的依赖方向检查。
- 逐步减少直接包含 `main.h`、`RobotConfig.h` 和整块 `Watch.h` 的共享模块。

### 七、持续验证和性能基线

- 持续检查运行主机单元测试和全部 GCC 目标。
- 实车记录控制周期抖动、错过周期、数据年龄、最长临界区、CAN 队列峰值和端到端延迟。
- 性能预算以实测基线为准，仿真估算只作为提前预警。

## 每个提交的最低验证

- `tools/build.ps1 -Action check`
- `tools/build.ps1 -Action gcc-build -Project all`
- `SENTINEL-M` Keil：0 错误、0 警告
- `git diff --check`

涉及公共启动、配置生成、故障输出或编译清单的提交，还要重建全部七个 Keil 工程。

## 哨兵验证记录建议

每次烧写至少记录提交号、运行时长、遥控与上位机链路、CAN 收发失败数、控制周期最大值、栈余量、最小剩余堆和日志丢弃数。
如果某一版出现退化，先回到上一提交复现；不要把多个阶段一起烧写后再猜是哪一层引入的问题。
