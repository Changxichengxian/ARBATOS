# 代码风格

这份规范面向 ARBATOS 的嵌入式 C/C++、PowerShell、Python 工具和项目文档。目标很简单：代码先让人看懂，再让机器执行；新增代码稳住风格，旧代码只在改到时顺手变清楚。

## 参考来源

本项目采用“中文可读、嵌入式适用、增量执行”的口径，参考但不照搬下面几份规范：

- `GB/T 28169-2011 嵌入式软件 C语言编码规范`：国家标准，说明嵌入式 C 代码本身就有明确的规范化要求。
- 华为云 LiteOS 编程规范：清晰、简洁、风格统一、通用性；并给出缩进、括号、注释、宏和头文件规则。
- OpenHarmony C 语言编程规范：中文环境下的开源 C 代码规范，适合做命名、注释和排版参考。

外部规范不能直接全文搬进仓库。一是版权不清，二是 ARBATOS 已经形成了自己的 `snake_case`、模块前缀、STM32/FreeRTOS 工程风格。这里采用的是可执行的项目版。

## 总原则

1. 清晰优先。命名、结构和注释要帮助后来的人判断“这段代码负责什么、边界在哪里、实车风险是什么”。
2. 局部一致。改旧文件时先跟当前文件风格走，不为了统一风格批量改名或重排全文件。
3. 小范围修改。功能改动、风格整理和重命名尽量分开，避免一次提交里混在一起。
4. 可编译可检查。改完至少跑 `tools/build.ps1 -Action check`；涉及 GCC 路线时跑对应 `gcc-build`。
5. 第三方代码、厂商库、协议原文和生成文件保持原样，除非有明确迁移任务。

## 命名

- C/C++ 新代码默认使用 `snake_case`。
- 文件名使用小写加下划线，和模块名、目录名保持接近。
- 函数名和变量名表达用途，少用缩写，不用拼音。
- 宏、编译开关和枚举值使用全大写加下划线。
- 跨模块可见的函数、变量和类型加模块前缀，例如 `sdlog_`、`can_tx_`、`robot_`。
- 文件内私有函数和私有变量加 `static`；已有 `s_`、`g_` 等前缀时沿用当前文件。
- 类型名沿用现有项目风格。已有 `_t` 的模块继续用 `_t`，已有枚举或结构体命名不要为了统一而批量改。
- 协议字段、寄存器名、外部 API 名按原始资料命名，避免把外部接口翻译成自造名字。

## 注释

新增注释主要用中文。下面这些情况可以保留英文：

- SPDX、许可证、版权和第三方文件头。
- 寄存器名、协议字段、CAN ID、库函数名、工具命令和外部标准名。
- 和上游库、厂商手册、数据手册完全对应的术语。

注释要写“为什么”和“边界”，少写“这一行做了什么”。推荐写：

- 模块入口前的阅读地图。
- 实车约束：总线负载、电源、机械限位、启动顺序、调试前提。
- 不明显的安全策略：失联后的输出、限幅理由、故障保持时间。
- 兼容性原因：为了旧日志、旧配置、厂商库或 Keil/GCC 差异保留的代码。

不推荐写：

- 把函数名逐字翻译一遍的注释。
- 已经过期的调试记录。
- 和代码行为不一致的历史描述。
- 大段英文解释但没有中文结论。

中文注释必须保持原编码，不要用 PowerShell 默认编码整文件覆盖含中文源码。

## 排版

- 新文件默认 4 空格缩进，不使用制表符缩进。
- 已有文件按当前文件缩进和括号风格，不做无关格式化。
- 新 C/C++ 文件默认函数左大括号另起一行，控制语句左大括号跟随语句。
- 一行只写一条语句。
- 一行尽量不超过 120 个字符；超过时按语义换行。
- `if`、`for`、`while`、`switch` 即使只有一行，也优先写大括号。
- `switch` 的 `case` 和 `default` 与项目现有缩进保持一致，并明确写出 `break`、`return` 或注释说明贯穿。

## 头文件

- 头文件应当自包含，单独包含也能通过编译。
- 头文件只放接口、类型、常量和必要宏，不放普通全局变量定义。
- 对外接口放在头文件，文件内辅助函数放在 `.c` 里并声明为 `static`。
- 包含顺序优先按当前文件风格。新文件建议先包含自己的头文件，再包含标准库、系统/RTOS、板级、项目模块。
- 不通过手写 `extern` 偷用别的模块内部符号，需要接口就补头文件。

## 宏和常量

- 多处使用的数字必须命名成宏、枚举或 `const`，单点使用但含义不明显的数字要写注释。
- 函数式宏的参数和整体表达式要加括号。
- 多语句宏使用 `do { ... } while (0)`。
- 复杂逻辑优先使用 `static inline` 或普通函数，少把流程藏进宏里。
- 宏定义末尾不加分号。

## 嵌入式边界

- 高速控制路径不要引入不可控耗时操作，例如文件写入、动态分配、长时间关中断、阻塞等待。
- 改 CAN、电机、IMU、SD、FreeRTOS 任务时，要同步考虑诊断、日志和失效状态。
- 涉及结构体协议、日志 payload、Flash/SD 文件格式时，必须说明版本和兼容策略。
- 改 Keil/GCC 共同代码时，优先用两条路线都能接受的写法。
- 生成文件、厂商库和第三方代码不要手工改；需要改时先说明来源和同步方式。

## 旧代码处理

旧代码风格不统一不单独扣分。真正要扣分的是继续扩大混乱：新改动和当前文件风格冲突、注释语言混杂、命名没有模块边界、或者为了“顺手整理”把功能改动埋在大范围格式化里。

以后改旧代码时按这个顺序处理：

1. 先保证行为正确、能编译、能检查。
2. 再把本次触碰到的命名和注释改清楚。
3. 最后只在必要时做小范围风格整理。

如果需要统一整个模块，单独开一次纯风格提交，提交说明里写清楚不改变行为。
